# 技术可行性分析：Windows 10 下 PS4 / PS5 手柄电量读取

> 对应需求文档第十一节。**本文结论全部来自本机实测与公开权威源码，不含推测。**
> 结论先行：**方案可行**，但存在两个必须正视的硬约束 —— ① 电量只有约 11 个
> 档位（每档 10%），拿不到 1% 精度；② Windows 10 的"专注助手/游戏模式"会
> 抑制 Toast 通知，因此低电量提醒必须走多通道兜底。

- 文档版本：1.3
- 验证环境：Windows 10 64 位（本机）、Python 3.13.14、hidapi 0.15.0
- 协议依据：Linux 内核 `drivers/hid/hid-playstation.c`、`hid-ids.h`

---

## 一、结论速览

| 待验证项 | 结论 | 风险等级 |
|---|---|---|
| PS4/PS5 手柄电量能否在 Windows 上读到 | **能**，走 HID 输入报告 | 低 |
| 是否有官方 API 直接给电量 | **没有**（索尼无消费级 SDK，XInput 只支持 Xbox） | 中 |
| 电量精度 | **仅约 11 档（每档 10%）**，无 1% 精度 | 中（不可消除） |

| 低电量提醒能否绕过免打扰 | **能**，靠多通道兜底，不依赖 Toast | 低 |
| 自启动推荐机制 | `HKCU\...\Run` 注册表键，免管理员 | 低 |
| 能否复用系统电池托盘图标 | **技术上不可行**，自绘 | 低 |

## 二、验证项 1：Windows 10 上读取 PS 手柄电量的数据源

### 2.1 候选方案排查

| 方案 | 可行性 | 结论 |
|---|---|---|
| `XInputGetBatteryInformation` | ✗ | `XINPUT_GAMEPAD` 结构体**根本没有电池字段**；该 API 只对 Xbox 手柄返回有效值，对 DS4 / DualSense 一律返回 0。**排除** |
| Windows.Gaming.Input (WinRT) | ✗ | `Gamepad` 类同样不暴露 PlayStation 手柄电量。**排除** |
| HID + `HidD_GetFeature` / `IOCTL_HID_GET_FEATURE` | △ | 部分手柄可用，但需向设备发送特性报告请求，兼容性依固件而异，且 DS4 蓝牙下需要先切换报告模式。作为**辅助**手段 |
| **HID 输入报告（Input Report）** | ✓ | 手柄**主动、周期性地**推送输入报告，报告里就带电量字节。无需请求、无需握手、最稳定。**采用** |
| 索尼官方 SDK | ✗ | 索尼不向 PC 端公开消费级手柄 SDK。**排除** |

**决策：直接读 HID 输入报告。** 这是 Linux 内核驱动采用的同一条路径，也是
Windows 上唯一经过大规模验证的可靠路径。

### 2.2 协议事实来源

索尼从未发布 DS4 / DualSense 的 HID 协议公开文档。事实上的公开规范是
**Linux 内核驱动 `drivers/hid/hid-playstation.c`**（由索尼工程师参与维护，
`hid-sony.c` 已被其取代并废弃）。本项目所有字节偏移、位域定义逐条对照该文件，
并在源码注释中标明出处。

### 2.3 实测验证方法

本机（开发机）没有实体 PS 手柄，因此采用两条独立证据链：

1. **静态核对**：逐行比对 `hid-playstation.c` 中的结构体布局与 `#define`，
   推导出原始缓冲区下标（见下表）。该文件已保存至 `_research/hid-playstation.c`。
2. **合成报告单测**：构造符合协议的报告字节串（含边界值、异常值、截断报告、
   错误报告 ID），验证解析器的偏移与位域解释正确。共 63 项自动化测试，全部通过。

> 说明：本机 `hid.enumerate()` 枚举到 0 个索尼设备，因此**无法**做真机读数验证；
> 这一点已在 README「已知问题」中如实标注，并提供了 `--dump-hid` 工具供用户
> 在接入手柄后自行采集真实报告进行核对。

### 2.4 最终确认的报告布局

**DualShock 4（PS4）** —— 电量字节位于 `status[0]`

| 连接方式 | 报告 ID | 报告长度 | 电量字节下标 | 说明 |
|---|---|---|---|---|
| USB | `0x01` | 64 字节 | **30** | `1 + 29`（报告 ID + 结构体内偏移） |
| 蓝牙（完整） | `0x11` | 78 字节 | **32** | `3 + 29`（ID + 2 字节保留 + 偏移） |
| 蓝牙（精简） | `0x01` | 10 字节 | **不存在** | 报告只到 offset 9，协议上**不含**电量字段 |

电量字节位域：

```
bit 0-3  BATTERY_CAPACITY   (GENMASK(3,0))  电量等级 0~10
bit 4    CABLE_STATE        (BIT(4))        1 = 已插入 USB 线
bit 5-7  保留
```

特殊值：容量 `11` = 已充满；`14` / `15` = 电压或温度异常 / 充电错误。

**DualSense（PS5）** —— 电量字节位于 `status[0]`

| 连接方式 | 报告 ID | 报告长度 | 电量字节下标 | 说明 |
|---|---|---|---|---|
| USB | `0x01` | 64 字节 | **53** | 驱动中 `&data[1]` + 结构内偏移 52 |
| 蓝牙 | `0x31` | 78 字节 | **54** | 驱动中 `&data[2]` + 结构内偏移 52 |

电量字节位域：

```
bit 0-3  BATTERY_CAPACITY   (GENMASK(3,0))  电量等级 0~10
bit 4-7  CHARGING_STATUS    (GENMASK(7,4))  充电状态
```

充电状态取值：`0x0` 放电、`0x1` 充电、`0x2` 已充满、`0xa`/`0xb` 异常、
`0xf` 充电错误。

### 2.5 已识别的设备 VID / PID

索尼 Vendor ID 固定为 `0x054C`。

| PID | 设备 | 家族 | 有无电量 |
|---|---|---|---|
| `0x05C4` | DualShock 4 (CUH-ZCT1) | DS4 | 有 |
| `0x09CC` | DualShock 4 (CUH-ZCT2) | DS4 | 有 |
| `0x0BA0` | DualShock 4 无线适配器 (CUH-ZWA1) | DS4 | 有（原样转发 DS4 报告） |
| `0x0CE6` | DualSense (PS5) | DualSense | 有 |
| `0x0DF2` | DualSense Edge (PS5) | DualSense | 有 |
| `0x0268` | DualShock 3 (PS3) | — | **无**，标注为不支持 |
| `0x03D5` | PS Move 控制器 | — | **无**，标注为不支持 |

后两项显式列入"识别但无电量"，避免用户接上后看到空白而误以为程序失效。

## 三、验证项 2：电量等级数量与精度上限

### 3.1 硬约束

DualSense 驱动注释原文：

```
Each unit of battery data corresponds to 10%
0 = 0-9%, 1 = 10-19%, .. and 10 = 100%
```

DualShock 4 同理：低 4 位取值 `0~10`，另有 `11`（已充满）与 `14`/`15`（异常）。

**结论：只有约 11 个档位，任何声称 1% 精度的实现都是在伪造数值。**
这是 HID 协议的物理上限，不是软件缺陷 —— 手柄固件本身只上报 4 bit。

### 3.2 本项目的处理方式

1. **原样保留原始等级**：`BatteryReport.level` 保存 0~10 的原始值，不做任何
   平滑或插值。
2. **百分比按区间中点换算**：与 Linux 驱动完全一致

   ```python
   battery_capacity = min(level * 10 + 5, 100)   # 0→5%, 1→15%, … 9→95%, 10→100%
   ```

3. **UI 明确标注精度边界**：悬停提示与菜单统一写"**约 72%**"，并附
   "**等级 7/10**"，让用户直接看到离散档位而非被假精度误导。
4. **低电量阈值按档位设计**：因为电量每 10% 才跳变一次，30% 阈值实际等价于
   "等级 ≤ 2"，20% ↔ "等级 ≤ 1"，10% ↔ "等级 0"。阈值去重状态机正是按
   这个粒度实现的（见 `notify/policy.py`），所以不会出现同一档位反复弹窗。
5. **异常值不当作 0%**：内核驱动在 `0xa`/`0xb`/`0xf` 时把电量置 0；本项目
   **不这样做** —— 否则会误触发"电量耗尽"告警。改为返回"电量未知 + 状态异常"，
   UI 明确显示异常，绝不伪造数字。

## 四、验证项 3：USB 与蓝牙的差异

| 差异点 | USB | 蓝牙 |
|---|---|---|
| 报告 ID | `0x01` | DS4 `0x11` / DualSense `0x31` |
| 报告长度 | 64 字节 | 78 字节 |
| 电量字节下标 | DS4=30 / DS=53 | DS4=32 / DS=54 |
| 报告频率（实测量级） | 约 250Hz~1kHz | 约 250Hz 左右 |
| 供电 | 有线，可能同时在充电 | 电池供电；DS4 蓝牙**可能**只发精简报告 |
| 特殊问题 | 无 | **DS4 蓝牙精简报告（`0x01`）不含电量字节** |

> **同一个报告 ID `0x01` 在两条总线上含义不同**，这是最容易读错位置的地方。
> 内核驱动 `hid-playstation.c` 的原文注释::
>
>     DualShock4 in USB uses the full HID report for reportID 1, but
>     Bluetooth uses a minimal HID report for reportID 1 and reports
>     the full report using reportID 17.
>
> 即 **`0x01` 只在 USB 上是完整报告**（电量在下标 30）；蓝牙上的 `0x01`
> 是精简报告（无电量），蓝牙的完整报告是 `0x11`（电量在下标 32）。
> 驱动用 `hdev->bus` 区分，本项目也**必须用 `transport` 区分**。

### 4.1 DS4 蓝牙精简报告的处理（重要）

DS4 通过蓝牙连接时，Windows 可能只让它发送精简报告（只有摇杆和按键），
**该报告中协议层面就没有电量字段**。Linux 驱动通过向设备发送特性
报告（Feature Report）请求，把 DS4 切换为完整报告模式。

本项目采用相同思路，在 `backend.request_ds4_full_report_mode()` 中发送
特性报告（报告 ID `0x02` / `0x05`）尝试切换；若切换失败，则：

- 返回 `ChargeState.UNKNOWN`（而非 `None`），上层据此知道"设备在传数据，
  只是没有电量"；
- 在菜单中标注"⚠"并在详情里说明原因，**不显示假数字**；
- 日志记录原始报告十六进制，便于排障。

**真机踩坑记录（1.2 修复）**：某些蓝牙栈会把 10 字节的精简报告**补齐到 64 字节**。
早期实现只看报告 ID 与长度，长度一"合格"就走了 USB 分支去读下标 30 —— 那里是
填充的 `0x00`，于是解析成「0 档 / 约 5%」，**在接入瞬间误触发一次低电量提醒**，
十几秒后才被真正的 `0x11` 报告纠正。日志里共出现 **3 次**
（`21:02:53`、`21:05:00`、`21:33:20`），形态完全一致：

```
21:02:53,034  电量更新 …：level=0 percent=5  source=ds4.usb.input0x01[30]   ← 误报
21:02:53,034  低电量提醒入队：DualShock 4 约5%（阈值 10，critical）          ← 误报
21:03:15,163  电量更新 …：level=6 percent=65 source=ds4.bt.input0x11[32]    ← 真实值
```

修复方式与内核一致：**判定分支必须同时看 `transport` 与报告 ID**，
蓝牙上的 `0x01` 一律按精简报告处理（等级未知），交给既有机制去切完整模式。
回归测试直接使用上述真机原始报告字节
（`test_bt_padded_minimal_report_is_not_usb_full`）。

### 4.2 连接方式判定

`hidapi` 的 `device_info` 提供 `bus_type`（USB / Bluetooth）。若该字段不可靠，
解析器会**按报告 ID 自动推断**连接方式（`0x11`/`0x31` → 蓝牙；`0x01` → USB），
两条路径互为兜底。

## 五、验证项 4：Windows 10 通知抑制行为与可靠兜底

### 5.1 问题

Windows 10 的 **专注助手（Focus Assist / 免打扰）**、**游戏模式**、
**演示模式** 会抑制 Toast（气泡）通知。如果只依赖 Toast，玩家在全屏游戏里
**恰好最需要低电量提醒的时候，提醒恰恰不会出现** —— 这是必须解决的矛盾。

### 5.2 检测机制（已实测可用）

使用 `shell32.SHQueryUserNotificationState`：

| 返回值 | 含义 |
|---|---|
| `1` QUNS_NOT_PRESENT | 用户不在（锁屏/屏保/未登录） |
| `2` QUNS_BUSY | 全屏应用（非 D3D）或演示中 |
| `3` QUNS_RUNNING_D3D_FULL_SCREEN | **全屏游戏（D3D 独占）** |
| `4` QUNS_PRESENTATION_MODE | 演示模式 |
| `5` QUNS_ACCEPTS_NOTIFICATIONS | **可正常显示通知** |
| `6` QUNS_QUIET_TIME | **专注助手 / 免打扰时段** |
| `7` QUNS_APP | Windows 应用全屏中 |

**本机实测**：正常桌面环境返回 `5`（QUNS_ACCEPTS_NOTIFICATIONS），
判定逻辑工作正常。

> 该 API 只能给出"系统层面是否抑制"，无法区分专注助手的"仅优先级通知"
> 模式。因此本项目的策略是：**被抑制时也绝不放弃提醒**，而是切换到不被
> 抑制的通道 —— 这是设计上的关键决策。

### 5.3 四通道提醒架构（不依赖单一通道）

| 通道 | 实现 | 是否受免打扰抑制 | 角色 |
|---|---|---|---|
| ① **托盘图标告警 + 闪烁** | 图标切为琥珀/红色告警态，闪烁 8 秒 | **否** | 主兜底，永远生效 |
| ② **系统提示音** | `winsound.MessageBeep` | **否** | 主兜底，永远生效 |
| ③ **Toast 气泡通知** | `Shell_NotifyIcon(NIF_INFO)` | **是**（可能被抑制） | 尽力而为 |
| ④ **自绘 Win32 弹窗** | 纯 ctypes 顶层窗口，`WS_EX_TOPMOST` | **否** | 抑制时自动升级启用 |

**升级逻辑**：`notifications_suppressed()` 返回 `True` 时，弹窗通道
（④）从"不弹"自动升级为"弹出"，补偿被抑制的 Toast。因此无论用户处于
哪种状态（全屏游戏、专注助手开启、锁屏），**至少有一个通道能触达用户**。

### 5.4 关于 tkinter

本机 Python **未提供 tkinter**，且 tkinter 会显著增大单文件 exe 体积、
在无控制台模式下偶发闪烁。因此弹窗通道改为**纯 ctypes 自绘 Win32 窗口**
（`notify/popup.py`），零额外依赖、无第三方库、完全可控。
`WS_EX_TOOLWINDOW | WS_EX_NOACTIVATE` 保证弹窗不抢焦点、不出现在 Alt-Tab 里，
不会打断游戏操作。

### 5.5 去重与防打扰策略

`notify/policy.py` 实现按"档位带"的状态机：

- 阈值降序为 `[30, 20, 10]`（百分比），对应档位 `2 / 1 / 0`；
- 每个手柄独立记录"已提醒到哪一档"；
- **同一档位内只提醒一次**，电量回到 5% 上下抖动也**不会**重复弹窗；
- **进入更低档位时重新提醒**（30→20→10 恰好三次）；
- 手柄断开时清除该手柄状态，重连后按当前电量重新判定；
- 多个手柄同时低电量时，提醒之间插入 `alert_min_gap_seconds`（默认 2 秒）
  的间隔，避免弹窗叠在一起。

## 六、验证项 5：开机自启动机制选型

### 6.1 候选方案对比

| 机制 | 需管理员 | 微软推荐 | 实现复杂度 | 结论 |
|---|---|---|---|---|
| **`HKCU\...\Run` 注册表键** | **否** | **是**（官方文档列为推荐做法） | 低 | **采用** |
| 启动文件夹 `shell:startup` | 否 | 否 | 低 | 次选，但单文件 exe 需额外维护快捷方式 |
| 计划任务（Task Scheduler） | 视配置 | 否 | 高（需 COM/XML） | 排除：行为重，易被安全软件误判 |
| 服务（Service） | **是** | 否 | 很高 | 排除：托盘程序不该做成服务 |

**决策：`HKCU\Software\Microsoft\Windows\CurrentVersion\Run`。**

### 6.2 实现要点（`autostart.py`）

- 值名固定为 `PSBatteryTray`，开关操作**幂等**，不会产生重复项；
- 写入的是**当前 exe 的绝对路径**（含 `--autostart` 标记），程序被移动或
  改名后路径失效，用户重新开关一次即可修正；菜单会检测并提示"路径指向旧版本"；
- 关闭时**只删除自己的值**，绝不触碰其它软件的自启动项（`other_entries()`
  仅用于发现潜在冲突，不做修改）；
- 读取 `...\Explorer\StartupApproved\Run` 判断是否被"任务管理器 → 启动"
  手动禁用：被禁用时**仅提示**，不自动改写（尊重用户意图）；
- 全程无 UAC 弹窗。

## 七、验证项 6：能否复用系统托盘电池图标

### 7.1 结论：技术上不可行，自绘

| 设想 | 可行性 | 原因 |
|---|---|---|
| 直接取用任务栏那个电池图标 | ✗ | 该图标由 `explorer.exe` **内部资源**渲染，无公开 API 可获取其 HICON，也无 API 能让第三方程序"接管"它 |
| `SHGetStockIconInfo` 取系统电池图标 | △ | 可取到通用电池图形，但**无法在图标上叠加数字/颜色**表示具体电量，且用户无法区分这是"笔记本电池"还是"手柄电量"，会造成严重误导 |
| `LoadIcon(IDI_BATTERY...)` | ✗ | Windows 未公开该 IDI 常量；即使能加载也不随电量变化 |
| **自绘多尺寸图标** | ✓ | 用 Pillow 按 Win10 扁平单色风格绘制，完全可控，且能随电量/主题变化 |

**决策：自绘图标。** 具体规格：

#### 几何（按参考图重绘，基准 16 格 × 10 格）

```
      +-------------------------+         外框 14×10，线宽 1 格
      |                         |
      |    +---------------+    |  +--+   正极 2×4，垂直居中
      |    |  电量块 10×6  |    |  |  |
      |    +---------------+    |  +--+
      +-------------------------+
```

| 部位 | 格坐标（半开区间） | 尺寸 |
|---|---|---|
| 整体字形 | — | **16 × 10** |
| 外框 | `(0, 0, 14, 10)` | 14 × 10，线宽 1 |
| 内腔 | `(1, 1, 13, 9)` | 12 × 8 |
| 电量块活动区 | `(2, 2, 12, 8)` | 10 × 6 |
| 正极凸起 | `(14, 3, 16, 7)` | 2 × 4 |

**核心**：电量块相对内腔**四周各内缩 1 格**，与外框之间形成一圈等宽留白。
是「整个电量区域向内缩进」，而不是「在电量条中间加一条线」。
满格 10 格宽 ⇒ **横向 1 格 = 10%**，与手柄 11 档电量一一对应
（0 档 → 0 格，10 档 → 10 格）。

#### 清晰度（关键决策）

「小尺寸锐利」这件事有两层，**缺一层就会发虚**。第二层是后来补上的关键修复。

**第一层：按目标像素尺寸直接算几何，不做任何图片缩放**

- 尺寸取自 `GetSystemMetrics(SM_CXSMICON)`，随 DPI 变化
  （100%→16、125%→20、150%→24、200%→32）；
- 几何**直接在目标像素网格上算**：外框线宽 `sw = round(size/16)`，外沿按 14/16
  取整，正极居中 —— 所有矩形边界都是**整数设备像素**。代码里**没有抗锯齿这一步**，
  自然也没有灰边；线宽随尺寸取整而非插值，外框四周用同一个 `sw`，因此**对称等宽**；
- 叠加图案在各自区域内按格等分取整，永远贴合；
- `.ico` 内含 **16/20/24/32/40/48/64/128/256** 九个尺寸，且**每个尺寸单独
  重绘**（自写 ICO 容器），而不是让工具从 256 逐档缩放。

**第二层：交给 Windows 的 HICON 尺寸必须严格等于托盘尺寸（本次实测修复）**

第一层做完后图标仍然发虚，实测证明**问题不在绘制，而在交付**：

| 环节 | 实测结果 |
|---|---|
| pystray `_win32.Icon._assert_icon_handle` 调用 `LoadImage(None, path, IMAGE_ICON, 0, 0, LR_DEFAULTSIZE \| LR_LOADFROMFILE)` | `LR_DEFAULTSIZE` 取的是**大图标**度量 `SM_CXICON` = **32**，不是托盘用的 `SM_CXSMICON` = **16** |
| 于是 16×16 源图被 **拉伸到 32×32** | 回读该 HICON：alpha 取值达 **46 种**（255, 254, 250, … , 8, 0），即边缘出现大量半透明灰边 |
| 通知区域再把它 **缩回 16×16** 绘制 | 第二次插值，1 像素宽的电池外框彻底糊掉 —— 这正是用户截图里"像被缩放过"的观感 |

**修复方案**：不再让 Windows 决定尺寸，改为 `CreateIconIndirect` 从**精确 DIB**
（`CreateDIBSection` + 预乘 alpha BGRA + 全零 1bpp 掩膜）直接包出 HICON。
图标尺寸就是图像尺寸，**代码路径里不存在任何缩放**。

实测对比（`python tools/verify_hicon.py`，报告见 `artifacts/hicon_verify.txt`）：

| 路径 | HICON 尺寸 | alpha 取值 | 中间 alpha 像素 | 结论 |
|---|---|---|---|---|
| pystray 原路径 `LR_DEFAULTSIZE` | **32×32** ❌ | 46 种 | 44 | 灰边 |
| `LoadImage` 显式 `cx=cy=SM_CXSMICON` | 16×16 | `[255, 0]` | 0 | 锐利 |
| **`hicon.create_hicon`（现方案）** | **16×16** ✅ | `[255, 0]` | **0** | **锐利** |

并且回读 HICON 像素与源图**逐像素一致**，尺寸**等于 `SM_CXSMICON`** 而非 `SM_CXICON`。

> 为什么必须这样：托盘图标最终只有 16~32 物理像素。只要交付给系统的句柄被拉伸过，
> 通知区域缩放回来时 1 格宽的外框必然出现灰边 —— 这与我们的绘制精度无关。
> 该结论已固化为回归测试（`tests/test_components.py::IconSharpnessTests`）：
> HICON 尺寸必须 `== SM_CXSMICON`，且像素与源图逐像素相等。

另一处工程细节：DPI 变化**无需重启**。每次刷新都重新读 `SM_CXSMICON`，
尺寸变了就按新尺寸重绘（日志记录 `托盘图标尺寸随 DPI 变化：16px → 20px`）。

#### 两套图标风格：win10（直角）/ win11（圆角）

任务栏图标本身没有 API 可以复用，只能自绘。为了让图标和系统观感一致，
内置两套风格，可在托盘右键菜单里随时切换（写入配置，重启后保持）：

| 风格 | 特征 |
|---|---|
| `win10`（默认） | 直角外框；沿用用户给定的基准图，**逐像素锁定** |
| `win11` | 外框 / 内腔 / 电量块 / 正极**按整数像素倒圆角**；其余与 win10 完全一致 |

关键是**圆角不能引入抗锯齿**。做法是在每个角的 `r×r` 方块内做整数像素的
圆形裁剪（`_rounded_pixels()`），像素要么整个画、要么整个不画，因此整张图标
仍然只有 alpha `0` 与 `255` 两种取值 —— 与前面「硬边」的结论一致。
半径按目标尺寸取整（`round(2.4·size/16)`）：16px 切掉 1 个角像素、32px 切掉 3 个，
与 Win11 实机观感吻合（参考截图上 30px 宽的字形，角上是 2 像素台阶过渡）。

两种风格**共用同一套几何**（`Geometry` 只是多了个 `radius`），所以电量表达方式
不会因风格而异：11 档填充宽度、外框线宽、正极位置全部相同。

> 保留差异可核对：`artifacts/icon_styles_compare.png`（两种风格 × 深/浅底 × 16/24/32px 并排）
> 与 `artifacts/icon_preview.png`（全状态预览，已含两种风格）。

#### 主题跟随：探测间隔是 30 秒 → 等同"不跟随"（1.3 修复）

`ThemeWatcher` 会轮询注册表判断任务栏亮/暗，但探测间隔原本是 **30 秒**
（且看门狗本身也是 30 秒一轮），于是用户在「设置 → 个性化 → 颜色」里一切换，
最长要等半分钟图标才变色 —— 体感就是"不跟随"。

真机实测：翻转 `SystemUsesLightTheme` 后，日志里 `20:37:02` 才出现
`检测到系统主题变化，已重新生成托盘图标`，确实能跟随，但延迟太长。

修复：把**主题复查**独立出来，每 **1 秒**读一次注册表（同一个 HKCU 下的 DWORD，
开销微秒级）；托盘重绘 / 菜单重建 / 检测层重启这些"重活"仍保持 30 秒一轮
（见 `app._start_watchdog` 的 `THEME_POLL_INTERVAL` 与 `WATCHDOG_INTERVAL`）。
这样切换亮暗后 1 秒内图标就会跟着换色。

#### 状态与主题

- **状态**：`MODE_LEVEL`（正常）/ `MODE_NONE`（无手柄：斜杠台阶）/
  `MODE_UNKNOWN`（电量未知：横杠）/ `MODE_ALERT`（低电量：琥珀或红 + 感叹号）；
- **充电不改变图形**：充电时同样按真实电量填充。早先跟随 Windows 系统电池图标
  画满块 + 抠闪电，但闪电盖住了电量条、看不出充到多少，而"充了多少"正是托盘
  图标最该回答的问题 —— 已改为与放电一致；充电状态由悬浮提示与菜单文字
  （"充电中 / 已充满"）表达。`charging` 参数仍保留，只用于**抑制低电量告警**
  （充电中不告警）。
- **一律纯主色**：四种状态用**同一个主色**、同一套不透明度（不透明），
  整张图标只有「透明(0)」与「主色(255)」两种像素。早期版本用整体半透明
  （alpha 105 / 200）表达"未激活/未知"，在深色任务栏上呈现为发灰，
  已改为纯图形区分（斜杠 / 横杠），并由单测锁定
  （`test_none_and_unknown_states_use_pure_primary_color`）；
- **主题自适应**：轮询 `SystemUsesLightTheme` / `AppsUseLightTheme`，
  深色任务栏用白图标、浅色任务栏用深色图标，避免"看不见"；
- **直角优先**：所有图案（含斜杠）都用 Bresenham 像素台阶实现，
  不用抗锯齿直线 —— 16px 下抗锯齿斜线会变成一条灰雾。

#### 刷新链路：节流绝不能丢状态（真机 bug 修复记录）

`Shell_NotifyIcon` 不宜高频调用，所以托盘刷新做了 150 ms 节流。但**「节流」不能
等于「丢弃」** —— 因为检测层是**变化驱动**的：只有电量档位 / 充电状态 / 连接状态
真的变化时才回调一次。一旦把某次刷新丢掉，就再也没有下一次回调来补救。

真机日志实测（2026-09-21）：

```
22:55:56,639  检测到手柄：DualSense (PS5) [USB / 054C:0CE6#…]     ← 快照①：电量未知
22:55:56,639  电量更新 …：level=8 percent=85 state=discharging      ← 快照②：85%
```

两条快照在**同一毫秒**先后到达（读取线程抢在扫描线程 `_publish()` 之前读到了电量），
快照②落在节流窗口内被直接 `return` 丢弃 → 图标停在「电量未知」，
**持续 3 分钟以上**直到电量下次变化才自愈。用户看到的就是
"明明读到了电量，图标却不显示"。

修复（三点，缺一不可）：

1. **尾部刷新**：被节流的刷新排队一次定时刷新，窗口结束后用**最新**快照重绘；
2. **状态未变则不推送**：画笔按 `(电量, 充电, 模式, 尺寸, 主题)` 缓存，同一状态
   返回**同一个图像对象**，用身份比较即可判断，因此尾部刷新几乎零成本；
3. **看门狗兜底**：每 30 秒用最新快照重绘一次。即使将来出现意料之外的丢失
   （异常、竞态），也能在 30 秒内自愈。

回归测试：`tests/test_components.py::TrayRefreshTests`
（被节流更新不丢失 / 完整生命周期 / 状态未变不重复推送）。

## 八、整体可行性结论

### 8.1 可行的部分（已验证）

- HID 输入报告路径稳定可靠，USB / 蓝牙均可读，字节偏移已逐条对照内核驱动；
- 低电量提醒通过四通道架构可绕过 Windows 免打扰，不会被游戏模式吃掉；
- 注册表自启动免管理员、幂等、可回退；
- 自绘图标在 Win10 深/浅主题下均清晰可辨；
- 零 tkinter / 零 pywin32 依赖，纯 `ctypes` + `hidapi` + `pystray` + `Pillow`，
  单文件 exe 体积可控。

### 8.2 不可消除的限制（必须在文档中如实告知用户）

1. **电量只有约 11 档（每档 10%），不存在 1% 精度方案。** 这是协议物理上限。
2. **DS4 蓝牙精简报告不含电量字段。** 已尝试特性报告切换，失败时如实显示
   "电量未知"而非假数字。
3. **异常电量值（电压/温度/充电错误）不映射为 0%。** 避免误触发耗尽告警。
4. **托盘图标可能被折叠进"隐藏的图标"面板。** 这是 Windows 10 的默认行为
   （非程序缺陷），用户拖拽出来即可固定。
5. **本机无实体手柄，真机读数未经端到端验证。** 已用合成报告 + 模拟器 +
   可视化工具覆盖全部逻辑路径；`--dump-hid` 供用户在真机上采集核对。

### 8.3 最终决策

**按上述方案实施。** 该方案在"真实可用 > 视觉花哨"的优先级下是最优解：
不伪造精度、不依赖可能被抑制的单一通知通道、不自作聪明地改写用户系统设置。
